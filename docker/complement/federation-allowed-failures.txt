# --- Upstream test-design race (our answer is spec-correct) ---
# The test samples eventB.AfterTimestamp and immediately has the remote
# user join; the 1ms tsBoundaryGuard protects the sample against eventB
# but NOT against the join that follows it. Our join handshake stamps the
# membership's origin_server_ts ~1.5ms after the sample, so ~20% of runs
# they share a millisecond and the backward search correctly returns the
# join (distance 0, ots <= ts) instead of eventB (MSC3030 says closest
# wins; Synapse can't lose this race only because its join path takes
# ≥10ms). Root-caused 2026-08-08; upstream fix = a tsBoundaryGuard sleep
# before the federation joins in room_timestamp_to_event_test.go.
#
# The race is in the shared fixture, so it is NOT confined to one leaf —
# it lands on whichever sibling happens to collide that run, and the
# single-leaf entry below was mis-scoped. Observed 2026-08-18 on the two
# paginate leaves, in back-to-back runs of branches that touch no
# federation code (PR #49 hit `(start)`, PR #53 hit `(end)`), each with
# the same signature: the query timestamp shares a millisecond with the
# join, and we correctly return the membership at distance 0 —
#
#   Want $Tp… (ts …967) given …985, but got $CW… m.room.member (ts …985)
#
# At ~20% per leaf, one of the three fails about half of all runs, which
# matches what CI did. So all three are listed. `looking_forwards` and
# the imported-event leaf are deliberately left OUT: they have never been
# seen flaking, and blanket-listing the family would blind the gate to a
# real pagination regression.
#
# These carry the `?` flaky marker: tolerated when they fail, and never
# reported stale when they pass. They pass most runs by construction, so
# without the marker the gate would stand there advising their removal —
# which would break the build on the next collision.
